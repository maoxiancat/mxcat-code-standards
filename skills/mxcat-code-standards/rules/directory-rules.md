# 目录规范

## 目录职责

| 类型 | 承载 | 不承载 |
| --- | --- | --- |
| `components` | UI 渲染、局部展示交互、视图组合 | 裸请求、协议适配、跨页面业务编排 |
| `utils` | 纯转换、格式化、无 UI 辅助逻辑 | React 状态、页面上下文、组件渲染 |
| `hooks` | 状态与数据获取编排、复用交互逻辑 | JSX 布局、协议与客户端细节 |
| `api` | 请求、客户端封装、协议适配、模型转换 | 页面状态、UI 组合、展示分支 |
| `assets` | 被源码 import 的图片、音频、字体、SVG | 按 URL 直接提供的站点根文件、SQL、业务源码 |
| `constants` | 路由 path、环境标记、storage key、选项和静态映射 | 类型契约、请求实现、展示组件 |
| `containers` | 非 Next 的挂路由页面、页面组合和高层编排 | 路由表、请求客户端、长期混杂的具体实现 |
| `types` | 类型、接口等编译期契约 | 运行时值、请求、UI |
| `styles` | 样式和样式变量 | 业务逻辑、请求、组件实现 |
| `public` | favicon、robots.txt 等按 URL 直接提供的站点根文件 | 被源码 import 的图片、音频、字体、SVG、业务源码 |
| `db` | SQL | 业务源码、静态资源、站点根文件 |
| `routes` | 路由表，以及路径与页面的装配 | 页面实现、请求客户端、业务转换 |

## 规则

- 应按照共享范围以及所需类型创建对应类型目录
- 如果项目中已经存在承担同类职责的目录，则复用该目录，不得在同层新造语义重复的新目录。
- 文件跨越这些职责边界时，将相应实现归位，页面保留组合关系。不要把筛选、请求、转换、弹窗与展示全部长期堆在一个入口，也不要为了拆分随机制造目录。
- 如果新增页面级或路由级入口，则放到仓库既有的页面层或路由层目录，由该入口承接路由装配与页面编排，不得把页面主体散落到共享组件层或临时目录。
- 如果逻辑只服务单个页面、路由或 feature，则优先与该页面或 feature 就近放置。
- 如果逻辑会被多个页面、多个业务域或多个 feature 复用，则放入项目既有的共享层目录。
- `components`、`utils`、`hooks`、`api`、`constants`、`types`、`styles` 类型目录应进行统一导出，沿用项目已有导出风格，例如 `index.ts`。
- 如果新增目录只是因为当前文件太大，则必须先判断职责边界，再按职责拆目录，不得随意把文件随意分散到多个目录。
- 页面入口代码放在项目既有的页面层，不要把页面编排逻辑塞进共享组件目录。
- 共享展示组件放在项目既有的共享组件层，不要把它们散落在多个页面目录里重复维护。
- 纯工具逻辑放在项目既有的工具层，不要藏在页面文件或组件文件尾部。
- 请求和协议适配放在项目既有的 service 或 api 层，不要直接散落到组件、页面或通用 util 中。

## 边界说明

- 本 skill 不强制规定页面层必须叫 `pages`、`containers` 或 `app`；沿用仓库既有主流结构。
- 框架中的特殊写法必须沿用框架的要求，如 Next 路由里的路由组 `(group)`、动态段 `[id]`、`[...slug]`、`[[...slug]]`、平行路由 `@slot`、拦截路由 `(.)`、`(..)`、`(..)(..)`、`(...)`、私有目录 `_folder` 和 `%5F` 等 nextjs 特殊写法保持框架写法。`page.tsx`、`layout.tsx`、`loading.tsx`、`error.tsx`、`not-found.tsx`、`template.tsx`、`default.tsx`、`route.ts` 等 nextjs 特殊文件名保持框架文件名。
